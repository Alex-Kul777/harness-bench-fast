# Гипотеза: DeepSeek Harness (dsh) × DeepSeek-V4.1-Flash лучше на «нерешаемых» задачах

Статус: **черновик дизайна эксперимента** (ветка `research/dsh-ds41flash-hardtasks`). Это план, не результаты.

## 1. Гипотеза
**H1.** На трудных задачах (long-context волна 392–411) связка **DeepSeek Harness (dsh) + `deepseek-ai/DeepSeek-V4.1-Flash`** даёт pass-rate выше, чем те же модель+уровень под **OpenClaw** и **Pi** harnesses.
**H0.** Разницы нет; наблюдаемое — шум / инфраструктурный артефакт / разный набор задач.

## 2. Что уже видно в существующих данных (разведка)
Прогоны по матрице «задача × конфиг» из `results/*.json`:

| Задача | Попыток | Прошли | Кто прошёл |
|---|---:|:---:|---|
| `task_392_manuscript_continuity` | 19 | **1** | **только dsh** (ds41flash off) |
| `task_403_binary_format_reverse` | 18 | **1** | **только dsh** (ds41flash off) |
| `task_398_card_game_engine` | 18 | **0** | никто |

Т.е. 2 из 3 «почти нерешаемых» — это **эксклюзивные** решённые dsh-прогоны. Это сигнал **за** H1, но:
- OpenClaw `oc_m66-*` (plain/ultra) на этих задачах отработали **подозрительно быстро** (task_392 — 60 с, task_398 — 70 с) → похоже на сбой/0-usage, а не честную попытку; сравнивать «как есть» нельзя.
- Наборы отличаются (dsh long = 6 задач: 392–395, 398, 403; OC m66 long = другой срез).
- Один прогон = `K=1` → на задаче с «1 из 19» шум огромен.

## 3. Дизайн проверки (что предлагаю)
**Задачи (hard set, n=3–5):** `task_392`, `task_398`, `task_403` (ядро) + при желании `task_393`, `task_394` (та же long-волна). Все — из long-контекста (timeout floor 7200 s).

**Конфиги (матрица):** `{dsh, openclaw, pi} × ds41flash`, фиксируем модель и уровень.

**Уровни ризонинга:** минимум два — `none/off` и один reasoning (например `medium`), т.к. dsh мапит `off→provider.reasoning=off`, а Cloud.ru «нет ризонинга» = `none` (см. §4). Это ещё и контроль: если dsh-эффект держится на обоих уровнях — это про harness, а не про reasoning.

**Повторы:** `K=3` на конфиг×задачу (минимум). При n такой малый никаких p-value — только «устойчивый сигнал / нет сигнала» + доверительные интервалы Уилсона на pass@1.

**Метрики:** pass@1; solve-rate по K; ₽/solve (из `summary.estimated_cost_rub`); время.

**Контроли:**
- Один `task_set_version` (0.16.0) и один коммит бенчмарка (не мержить upstream).
- Одинаковый ключ/квота; прогнать preflight-`curl` (HTTP 200) на модель.
- Изоляция: dsh (`--permission-mode workspace-write`, свой dsh-home), OC, Pi — в отдельных workspace.
- **Починить/исключить** битые OC-прогоны (0-usage) — иначе сравнение нечестное.
- Сначала **пилот 1 задача × 3 конфига × 1 повтор** (смоук), потом полный набор.

**Команды (эскиз):**
```bash
# dsh
python3 run_dsh_bench.py --tasks task_392_manuscript_continuity,task_398_card_game_engine,task_403_binary_format_reverse \
  --thinking medium --json-output results/dsh_hard_tasks_ds41flash_medium.json
# openclaw / pi — аналогично их раннерами (--tasks ..., тот же уровень)
```

**Критерий «гипотеза подтверждена» (пре-регистрация):** dsh решает ≥2 из {392,403}`task` при `K=3`, а oc и pi — 0; эффект воспроизводится на обоих уровнях ризонинга.

## 4. Уровень ризонинга — как правильно определить и проверить
Ключевой риск: «мы думаем, что задали off/medium, а провайдер всё равно/иначе рассуждает». Протокол:

1. **Лестница уровней (per-model):** по скиллу `cloudru-model-reasoning-probe` — прогнать `reasoning_effort` по кандидатам (`none,minimal,low,medium,high,xhigh,max`) и читать **HTTP** (200=принят, 400=нет). Cloud.ru **не имеет `off`**; «нет ризонинга» = `none`. Не парсить тело 400 (там generic `invalid_parameter`).
2. **Доказать, что модель реально рассуждает:** повторить с валидным уровнем (напр. `high`) и требовать **непустой `message.reasoning`** (не `reasoning_tokens`: Cloud.ru отдаёт 0 там даже при reasoning).
3. **Согласовать с раннером:** accepted-имя уровня берётся из ошибки harness-а (напр. `Use one of: off, minimal, low, medium, high, ultra`) — `--help` может рекламировать верхний тир, который модель отвергает (`max` vs реальный `ultra`). Для dsh маппинг `off/none → provider.reasoning=off`, остальные — verbatim (`THINKING_LEVELS` в `run_dsh_bench.py`).
4. **Проверить, что флаг не «UI-only»** (по скиллу `pi-thinking-flag-verification`): A/B на ОДНОЙ дешёвой задаче `none` vs `high`; сравнить наличие/объём reasoning (direct API `message.reasoning` + логи раннера). Известный кейс: Cloud.ru **игнорировал** thinking-флаг у GLM-5.2 (37 vs 39 reasoning токенов) → флаг был no-op. Проверять ДО большого прогона.
5. **Смоук уровня:** один дешёвый task на целевом уровне — требовать реальные действия и токены; волна с 0 pass и ~0 токенов = инфраструктурная ошибка, а не «модель не решает» (см. `errorMessage` в `/tmp/<runner>_out_*.ndjson`).
6. **Пилот по ₽:** сравнить `none` vs один reasoning на малой волне — «no reasoning = дешевле» НЕ постулировать (unguided-ретраи иногда дороже).

> Особый нюанс для dsh: раннер пишет `thinking: off|none` в результаты, но **per-task reasoning-токены не сохраняет** (@см. entry keys), поэтому «реально ли рассуждалось» надо фиксировать через direct-API `message.reasoning` и/или NDJSON-лог `dsh`, а не из `results/*.json`.
