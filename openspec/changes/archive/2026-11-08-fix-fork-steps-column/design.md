# fix-fork-steps-column — design

## Контекст

- Артефакт прогона (JSON) несёт `tasks[]`, где у каждой задачи есть `agent_steps`
  (для OpenClaw = `toolSummary.calls`) и токены/секунды.
- Агрегат лежит в `summary`: `total_seconds`, `total_input_tokens`, … — но `total_steps`
  в OpenClaw-артефакте **отсутствует** (раннер `run_openclaw_bench.py::_write_results`).
- Спека `benchmark-runs` («Единый формат результата») уже требует `total_steps` →
  текущие артефакты **не соответствуют спеке** (compliance-баг, а не новая фича).
- Читающие генераторы берут **только агрегат**, поэтому колонка `Steps` = `—`.

## Решения

### D1. Fallback в генераторах (defensive)

`build_fork_home.py` и `build_fork_results.py` получают единый приоритет источников:
`summary.total_steps` → top-level `steps` → Σ `tasks[].agent_steps`. Общий helper, чтобы
обе поверхности считали одинаково (spec: «единый источник»).

- Плюсы: мгновенно закрывает **всю историю** (все OC-файлы) на обеих поверхностях и в
  обеих локалях; устойчиво к будущим артефактам без агрегата.
- Минусы: логика появляется в двух местах → выносим в один импортируемый helper.

### D2. Эмиссия агрегата в раннере (root fix)

`run_openclaw_bench.py::_write_results` пишет `summary.total_steps = Σ agent_steps`
(+ симметрично в `tokens`/`total`). Восстанавливает соответствие `benchmark-runs` и
делает артефакт самодостаточным (как у Pi/Hermes).

- Плюсы: корректность данных «у источника»; будущие прогоны не зависят от fallback.
- Минусы: правка в другом репозитории (`openclaw-workspace`) → отдельная ветка.

### D3. Бэкфилл исторических артефактов

В закоммиченные `results/oc_shotlist_*.json` добавляется `summary.total_steps`, равный
сумме их же `tasks[].agent_steps` (значения: 247/120/328/148/237/244/224/244). Без
пере-прогонов; чистая, проверяемая арифметика.

- Плюсы: артефакты становятся согласованными; генерируемый output не «дрожит».
- Минусы: правит исторические данные (только добавляя отсутствующее поле).

### D4. Определение метрики

`Steps` := число шагов агента = Σ per-task `agent_steps` (= `toolSummary.calls`).
Смысл метрики **не меняется**; меняется только способ её получения для рендера.

## Альтернативы и почему отклонены

- **Только D3 (бэкфилл 3 файлов):** хрупко — следующий OC-прогон снова без агрегата.
- **Только D2 (раннер):** не чинит уже лежащие артефакты и историю.
- **Правка только в одном генераторе:** нарушает spec «единый источник».

## Решения по проверке

- `python3 scripts/build_fork_results.py --check/--lint` → 0.
- `python3 scripts/build_fork_home.py --check` / `build_fork_pages.py --check` → 0.
- Новый `tests/test_fork_steps_fallback.py`: (a) fallback считается из `tasks[]`;
  (b) при наличии агрегата берётся агрегат; (c) обе поверхности дают одно значение.
- `tests/test_fork_bilingual.py` остаётся зелёным (паритет RU/EN).
- `npx -y @fission-ai/openspec@1.16.0 validate --all --strict` → 0.

## Ветки (не мешать main)

- `harness-bench-fast`: ветка `fix/fork-run-steps` (генераторы, бэкфилл, тесты, спека).
- `openclaw-workspace`: ветка `fix/oc-runner-total-steps` (эмиссия `total_steps`).
- Обе — от `main`; мерж/пуш — по отдельной команде владельца.
